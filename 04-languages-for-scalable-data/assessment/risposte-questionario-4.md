### 1. Explain the design goals behind Python as a programming language and discuss how these goals influence its typical areas of application. Your answer should refer to language characteristics such as typing, interpretation, readability, and ecosystem.
Python nasce con Guido van Rossum come linguaggio semplice e leggibile, a metà strada tra la shell e il C, pensato inizialmente per lo scripting di sistema. È un linguaggio interpretato, quindi non richiede compilazione e implementa una REPL interattiva. Di base è tipizzato dinamicamente,  usa l'indentazione come sintassi per favorirene la leggibilità. Nel tempo si è aggiunto un ecosistema di librerie enorme funzionali a tanti domini applicativi: scripting e automazione, prototipazione rapida, notebook per analisi dati e machine learning, sviluppo web. La semplicità tuttavia si paga con prestazioni e parallelismo che in Python puro sono modesti, per cui il calcolo pesante è delegato a librerie in C, C++ o Rust.
### 2. Discuss the scenarios in which Python is preferred over Java, providing concrete examples from data science or machine learning. Explain why Python’s features and libraries make it particularly suitable for these domains.
Python è preferibile quando contano velocità di sviluppo ed esplorazione interattiva più delle prestazioni del codice scritto a mano. Ad esempio, nella data science il lavoro è iterativo: caricare un dataset con pandas, esplorarlo e visualizzarlo in un notebook Jupyter, provare modelli con scikit-learn, addestrare reti neurali con PyTorch o TensorFlow. Si fa con poche righe e si vede subito il risultato, senza ricompilare che è fondamentale per figure di più alto livello che non vogliono interessarsi di dettagli implementativi. Le librerie sono il vero vantaggio: il calcolo gira in codice nativo ottimizzato e Python fa da orchestratore. Java richiederebbe più codice e ha un ecosistema per il machine learning meno ricco di Python
*Esempio:* confronto tra il ciclo compila-esegui di Java e il notebook. In Java ogni tentativo richiede di ricompilare e rilanciare tutto; in un notebook il dataset resta in memoria e si cambia una cella alla volta, quindi l'esplorazione diventa una conversazione con i dati.
### 3. Analyze the advantages and drawbacks of the Python GIL with respect to concurrency and parallelism. In your answer, distinguish between CPU-bound and I/O-bound workloads.
Il GIL è un lock dell'interprete CPython che permette a un solo thread per processo di eseguire bytecode alla volta. I vantaggi: interprete più semplice, reference counting senza lock su ogni oggetto, programmi single-thread più veloci, integrazione facile con librerie C non thread-safe. Lo svantaggio è che i thread non danno parallelismo reale sul calcolo. Con carichi CPU-bound in Python puro più thread non accelerano, anzi possono rallentare. Con carichi I/O-bound un thread in attesa di rete o disco rilascia il GIL, e molti thread avanzano utilmente in concorrenza. Il GIL non rende thread-safe il codice applicativo: operazioni come `x += 1` non sono atomiche.
### 4. Explain how Python applications can still achieve parallelism despite the presence of the GIL. Discuss the role of multiprocessing, external libraries, or native extensions.
Il GIL vale per processo, quindi la prima strada è `multiprocessing` (o `ProcessPoolExecutor`): più processi, ognuno con il proprio interprete, usano tutti i core, al costo di più memoria e di comunicazione tra processi. La seconda sono le librerie esterne: NumPy, SciPy e PyTorch eseguono il calcolo in codice nativo che rilascia il GIL ed è spesso già parallelo (BLAS, OpenMP, GPU). La terza sono le estensioni native in C, Cython con `nogil` e `prange` o Rust con PyO3, e i JIT come Numba. Per carichi I/O-bound bastano thread o `asyncio`. Su larga scala Dask o Spark distribuiscono il lavoro, con Python come orchestratore.
### 5. Describe the core characteristics of Java that support the “Write Once, Run Anywhere” (WORA) principle. Explain the role of the Java Virtual Machine (JVM) and bytecode in achieving platform independence.
Java separa compilazione ed esecuzione. Il compilatore non produce codice macchina per una CPU specifica ma bytecode, un linguaggio intermedio standard e indipendente dalla piattaforma. Il bytecode è eseguito dalla Java Virtual Machine, disponibile per ogni sistema operativo e architettura, che lo interpreta e compila con il JIT le parti più usate in codice nativo. Così lo stesso file .class gira su Windows, Linux, macOS o dispositivi embedded senza ricompilare. Contribuiscono anche la specifica rigorosa del linguaggio, con dimensioni dei tipi primitivi fissate e niente comportamenti dipendenti dall'hardware, e una libreria standard ampia che astrae file, rete e thread.
### 6. Explain why Java is often chosen for large-scale, enterprise-level applications. In your answer, reference object-oriented design, concurrency control, and database connectivity.
Java unisce struttura, affidabilità ed ecosistema. La programmazione a oggetti, con package e moduli, permette di organizzare codebase grandi in componenti incapsulati e riusabili, gestiti da team diversi, e la tipizzazione statica rende sicuri i refactoring. Per la concorrenza offre thread nativi, `synchronized`, lock e il package `java.util.concurrent`, adatti a server che gestiscono molte richieste insieme. Per i database c'è JDBC, un'API standard per qualsiasi database relazionale con supporto alle transazioni, e sopra framework come Hibernate e Spring. Si aggiungono la JVM, che dà portabilità e prestazioni stabili grazie al JIT, e la retrocompatibilità nel lungo periodo.
*Un caso dal mio lavoro:* in un servizio Spring Boot in produzione su Kubernetes sincronizziamo periodicamente dei dati da un sistema esterno verso un database Oracle. Il client remoto sta dietro un'interfaccia con il mapping dei DTO isolato, così cambiare il formato dei dati in ingresso non tocca la logica applicativa. Il punto delicato è la concorrenza: girando su più repliche, lo stesso job schedulato partirebbe più volte in parallelo sugli stessi record, quindi usiamo un lock distribuito su tabella (ShedLock) per garantire una sola esecuzione, con le scritture in transazione e un pool di connessioni dimensionato sui limiti del database.
### 7. Given a performance-critical numerical application, justify whether you would choose Java, pure Python, or an optimized Python approach (e.g., Cython or PyPy).
Dipende da dove si concentra il calcolo, ma scarterei il Python puro: tipi dinamici, oggetti boxed e GIL lo rendono lento nei cicli numerici. Se il lavoro si esprime come operazioni su array, sceglierei Python con NumPy, che esegue i cicli in codice nativo. Se ci sono cicli propri non vettorizzabili, userei Cython con tipi dichiarati o Numba, che danno speedup di uno o due ordini di grandezza con poche modifiche; PyPy aiuta sul Python puro ma è meno compatibile con le estensioni C. Java è la scelta migliore se l'applicazione è un servizio di lunga durata che richiede multithreading reale e prestazioni prevedibili, al costo di più codice e meno librerie scientifiche.
### 8. Give one example of an application better suited for Python and one better suited for Rust, and briefly explain why.
Per Python: un'analisi esplorativa su un dataset di vendite in un notebook, con pandas e grafici, dove i requisiti cambiano spesso e conta vedere subito i risultati; le prestazioni le garantiscono le librerie, ciò che conta è la velocità di sviluppo. Per Rust: un servizio di ingestione che riceve e valida milioni di eventi al secondo, o un motore di dataframe come Polars. Servono latenza bassa e prevedibile, uso efficiente di tutti i core e affidabilità nel tempo, che Rust offre senza garbage collector e con thread sicuri verificati dal compilatore. Le due scelte si combinano: prototipo in Python, parte critica in Rust richiamata da Python.
### 9. Why is Rust described as enabling predictable performance in large-scale systems?
Rust non ha garbage collector: la memoria è gestita a compile time con ownership e borrowing, e ogni valore viene liberato in un punto preciso, quando il suo proprietario esce dallo scope. Non ci sono quindi pause di raccolta dal momento imprevedibile, che nei sistemi grandi e time-critical creano picchi di latenza. Il codice è compilato ahead-of-time in codice nativo, senza warm-up del JIT né deottimizzazioni a runtime. Le astrazioni sono a costo zero: generics e iteratori diventano codice pari a quello scritto a mano. Il runtime è minimo e il layout dei dati in memoria è controllabile. Il risultato non è solo velocità, ma bassa varianza delle prestazioni.
### 10. Why is Rust particularly suitable for highly concurrent, multithreaded applications?
I thread di Rust sono thread del sistema operativo e girano davvero in parallelo, senza lock globale. La differenza è che il compilatore impedisce i data race: le regole di borrowing ammettono più riferimenti in lettura oppure un solo riferimento mutabile, mai insieme. I trait `Send` e `Sync` stabiliscono quali tipi si possono trasferire o condividere tra thread, quindi usare un tipo non sicuro in un altro thread è un errore di compilazione. Lo stato condiviso passa da tipi espliciti come `Arc<Mutex<T>>`, dove il mutex possiede il dato e non ci si accede senza il lock. Si ottiene concorrenza efficiente con garanzie a compile time, anche se deadlock e race condition logiche restano possibili.
